# RFC 2116과 allocation failure

RFC 2116, “Alloc Me Maybe”의 질문은 “메모리 사용량을 어떻게 제한할까?”가 아니다. 핵심 질문은 **collection allocation이 실패할 수 있다는 사실을 필요한 시스템 코드에서 어떻게 다룰 것인가**다.

## 당시 문제

`Vec::push`, `String` growth, `HashMap::insert`, `collect`는 내부에서 allocation할 수 있지만 일반 API는 `Result<_, AllocError>`를 반환하지 않는다. RFC는 이 developer model을 **infallible collection allocation**이라고 불렀다.

이 선택에는 이유가 있다.

- 대부분의 application은 모든 allocation failure를 복구할 수 없다.
- 드물고 테스트되지 않은 error path가 더 많은 bug를 만들 수 있다.
- ecosystem의 모든 trait와 API에 allocation error를 전달하면 복잡도가 크게 증가한다.

그러나 embedded, Gecko, server, runtime/DB는 서로 다른 복구 요구를 가진다. RFC는 database를 query language를 실행하는 runtime과 비슷한 대상으로 언급한다.

## RFC의 두 제안

```text
allocation failure
    ├─ unwinding 가능한 server
    │    └─ oom=panic 제안 → task boundary에서 catch
    └─ no-unwind runtime/embedded
         └─ try_reserve → Result로 pre-allocation 실패 처리
```

두 제안의 현재 상태를 분리해야 한다.

- `try_reserve` 계열은 `Vec`, `String`, `HashMap` 등 stable standard library API로 정착했다.
- RFC에 적힌 Cargo의 `oom = "panic"` profile 설정은 현재 stable Cargo profile option으로 제공되지 않는다.
- `std`를 링크하는 일반 구성에서 `handle_alloc_error`의 문서상 기본 동작은 stderr 메시지 뒤 abort다. Panic 전략과 OOM 전략을 같은 설정으로 보지 않는다.

## 왜 `try_reserve`인가

`try_push(value)`가 실패하면 ownership을 소비한 `value`를 어떻게 돌려줄지 API가 복잡해진다. `extend(iterator)`는 중간까지 소비한 iterator와 이미 추가한 element를 어떻게 표현할지도 결정해야 한다.

RFC는 먼저 작은 primitive를 선택했다.

```rust
use std::collections::TryReserveError;

fn copy_checked(input: &[u8]) -> Result<Vec<u8>, TryReserveError> {
    let mut output = Vec::new();
    output.try_reserve(input.len())?;
    output.extend_from_slice(input);
    Ok(output)
}

fn main() {
    assert_eq!(copy_checked(b"memory").unwrap(), b"memory");
}
```

이 패턴은 allocation 가능 지점을 critical section 앞쪽으로 끌어올린다.

```text
필요량 계산
  ↓
try_reserve
  ├─ Err → 작업 시작 전 실패
  └─ Ok
       ↓
capacity 안에서 push/insert 수행
```

## 세 가지 한계

1. **Overcommit:** 성공이 physical memory 확보를 뜻하지 않는다.
2. **Transitive allocation:** 호출한 dependency와 formatting/clone이 별도 allocation을 할 수 있다.
3. **Unknown size:** filter, streaming input, graph algorithm은 upper bound를 정확히 알기 어렵다.

따라서 다음 등식은 성립하지 않는다.

```text
try_reserve == memory admission == OOM immunity
```

## Server/DB에서의 현대적 해석

RFC 2116은 application budget을 대신하지 않는다. 오히려 다음 chain의 가운데 한 고리를 강화한다.

```text
admission reservation
    ↓
fallible collection pre-allocation
    ↓
execution
    ↓
spill / eviction / release
```

Application reservation은 논리적 사용 권한이고 `try_reserve`는 실제 collection allocation failure를 전달하는 API다. 둘을 조합하되 동일시하지 않는다.

## 보장 경계

### 이 장이 보장하는 설명

- RFC 2116의 원래 문제, user profile, 최소 fallible allocation 접근
- 현재 stable Rust에 남은 `try_reserve`와 구현되지 않은 `oom=panic` profile 제안의 구분

### 이 장이 보장하지 않는 것

- RFC 문서의 모든 제안이 현재 Rust에 구현되었다는 주장
- `try_reserve`가 dependency allocation이나 page fault OOM을 막는다는 주장
- 모든 algorithm을 allocation-free critical section으로 만들 수 있다는 주장
